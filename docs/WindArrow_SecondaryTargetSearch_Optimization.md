# 风矢穿林：副箭目标搜索优化设计

## 结论

第一阶段优先优化 **视线检测的执行顺序**，而不是建立全局目标缓存、额外空间索引或复杂射线批处理。

当前搜索在候选经过合法性、距离和前半平面过滤后，会先对每个候选执行一次方块视线射线检测，再从可见目标中选最高优先级。可见性检测是相对昂贵的操作，但只需要知道“排序最高的可见目标”即可；不必先证明所有低优先级目标也可见。

推荐的低风险方案是：保留现有候选范围和选敌评分，预计算每个候选的排序信息，按原有优先级从高到低遍历，只对当前候选做视线检测，遇到第一个无遮挡目标立即返回。

## 当前行为基线

当前实现位于 `WindArrowSpell.findSecondaryTarget`：

1. 查询施法者包围盒向外扩展 16 格的范围。
2. 排除施法者本身、死亡/移除/无敌/旁观目标、盟友，以及创造模式或旁观模式玩家；排除主箭目标。
3. 保留与施法者距离不超过 16 格的目标。
4. 只考虑水平前半平面，条件为水平朝向点积不小于约 0。
5. 对所有通过几何过滤的候选分别执行 `level.clip`，检查施法者眼睛到目标包围盒中心之间是否被方块遮挡。
6. 在可见候选中按以下优先级选择：
   - **自然附着目标优先**；
   - 同优先级下，最大化 `horizontalDot * 100 - distance`。

上述规则属于现有玩法语义。第一阶段必须保留范围、合法目标判定、前半平面、遮挡规则、自然附着优先级和评分公式，不借优化之名调整选敌手感。

## 第一阶段：低风险优化

### 1. 先做便宜的过滤

保持 Minecraft 现有的实体空间查询，不增加新的空间索引。先排除非法目标、主箭目标、超出 16 格距离的目标，再计算水平前半平面条件。对不合格候选不做附着查询或视线射线检测。

### 2. 每个候选只计算一次排序元数据

为每个通过几何过滤的目标临时记录：

- 实体引用；
- 是否持有有效自然附着；
- 水平朝向点积；
- 当前评分 `horizontalDot * 100 - distance`。

自然附着只在此轮搜索读取一次，评分里的目标中心、水平归一化向量和距离也只计算一次。元数据仅存在于本次方法调用，不跨 tick 缓存，所以目标移动或附着变化不会留下过期状态。

### 3. 按原有优先级排序，遇到第一个可见目标就停止

对候选按“自然附着优先、评分从高到低”进行稳定排序，然后依次调用现有的 `hasLineOfSight`：

- 当前候选可见：立即返回该目标；
- 当前候选被方块遮挡：检查下一位；
- 全部被遮挡或候选为空：返回 `null`。

这与“检查所有候选的视线，再从可见候选中取最大值”的目标选择逻辑等价：最终仍是**优先级最高的可见合法目标**。区别在于，找到结果后不会继续为更低优先级候选执行不必要的 `level.clip`。

若有 (N) 个几何候选，当前路径会对全部 (N) 个候选做视线检测；新路径的检测次数取决于第一个可见候选的排名，最好情况为 1，最坏情况仍为 (N)。候选排序会增加 (O(N\log N)) 的轻量 CPU 与临时列表成本，因此必须用剖析数据验证净收益，不能仅凭理论直接认定整体一定更快。

### 4. 保持服务端权威与现有结算路径

搜索仍然只在服务端的箭矢 Recast 中执行。返回目标后，仍由现有逻辑负责生成项目内 Blast 光束、消耗自然附着、结算强化爆发和直击伤害、发放猎矢奖励。此优化不应改动伤害、粒子、光束同步或 Recast 状态。

## 性能验证方案

在开发环境使用临时或可关闭的诊断计数；不要在每次搜索中打印日志。对同一场景分别测试现有版本与优化版本，至少记录：

- 每次搜索的实体查询候选数；
- 通过合法性/范围/半平面过滤后的候选数；
- 实际执行的视线射线检测次数；
- 搜索耗时的 p50 / p95；
- 选出的目标与原实现是否一致。

场景至少覆盖空场景、普通战斗、多个目标、多个自然附着目标、前方目标全部被遮挡、主箭与副箭应排除同一目标等情况。尽量让测试目标位置、附着状态和方块遮挡一致。

验收条件：

- 固定场景中选敌结果与基线一致；
- 伤害、附着消耗、强化爆发、资源奖励和光束端点行为不变；
- 存在多个候选时，平均视线射线检测次数应下降；
- 稀疏场景下 p50 / p95 不出现有意义的回退；
- 无跨 tick 缓存，因此无需新增目标移动、死亡、卸载或附着变更的失效管理。

## 暂不采用的方案

- **跨 tick 目标缓存**：一次攻击只需选一个副箭目标；候选会移动、死亡、切维度或改变附着，缓存失效成本可能超过收益。
- **自建空间索引 / 全局目标注册表**：Minecraft 已有实体空间查询，当前没有测量证据说明查询本身是主要瓶颈。
- **复杂射线批处理**：目前每轮至多选择一名副箭目标，先排序后短路就能减少大量无用射线，不需要引入额外执行系统。
- **改变选敌评分**：把距离权重、前方角度或自然附着优先级纳入另一个公式会改变玩法，应与性能优化分开讨论。
- **默认永久启用的细粒度日志**：会给服务端引入额外负担并污染测量结果。

## 后续决策门槛

只有基线剖析显示实体查询本身占据显著耗时，才继续研究收紧空间查询范围；只有优化后仍有证据显示附着查询或排序是热点，才考虑更进一步的结构调整。冰晶粒子等其他系统继续单独剖析，不与副箭搜索优化绑在同一改动中。

## 实施状态

本文是设计说明，不代表代码已按该方案修改，也不代表性能收益已经通过实测确认。实现前先取得基线；实现后运行构建、目标一致性回归和服务端耗时对比。
